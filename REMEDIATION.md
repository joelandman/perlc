17. ~~**Fix D38b: `s/$/text/` segfault (zero-width regex-substitution match)**~~ — FIXED

23. ~~**Fix D23: regex literals collapsed `\\` into a single `\`, silently changing match semantics**~~ — FIXED
    - Root cause: the lexer's `readRegex()` special-cased `\\` in the source and collapsed it to a single `\` in the pattern string handed to PCRE2, while passing every *other* backslash-escaped pair (`\d`, `\s`, `\/`, etc.) through unchanged (both characters) — an inconsistency, and wrong. PCRE2 needs to see `\\` exactly as written to interpret it as "one literal backslash"; collapsing it first turned the following character into part of an unintended escape sequence. `/a\\d/` (literal backslash then "d") silently became `/a\d/` (the digit metaclass) with no error — a silent, wrong-match bug for any pattern containing a literal backslash.
    - Fix: removed the special case entirely. Every backslash-escaped pair is now passed through to PCRE2 unchanged, exactly like the general (non-`\\`) branch already did. PCRE2 does its own escape interpretation and tolerates a redundant escape of the delimiter character (`\/`) fine — no lexer-side special-casing needed for that either. `s///`'s lexer (`readSubst`) never had this bug — its equivalent loop already passed every escaped pair through unconditionally, so no change was needed there.

24. ~~**Fix D35: `Carp::croak`/`confess` bypassed `eval` via `exit(1)`, plus a crash and a data-corruption bug found while fixing it**~~ — FIXED
    - Root cause (D35 itself): `perl_carp_croak()` called `fprintf(stderr,...)` then `exit(1)` directly, completely bypassing the die/eval/longjmp mechanism. The standard `eval { croak(...) }` pattern for turning a library error into a catchable exception killed the entire process under perlc instead of setting `$@` and continuing.
    - Fix: route `perl_carp_croak()` through the existing `perl_die()` instead of duplicating (and getting wrong) its own exit logic. `perl_die()` already had the correct dual behavior — longjmp to the nearest eval (setting `$@`) if one is active, or print to stderr and `exit(1)` at top level if not. `codegen.cpp` already routes both `croak` and `confess` through `perl_carp_croak`, so both are fixed by this one change.
    - **Blocking crash found and fixed as a direct dependency**: the standard error-rethrow idiom `eval {...}; die $@ if $@;` passes `$@` to `die()` as the exact same cell it was just written into (`perl_get_dollar_at()` returns the live global's address, not a copy) — i.e. self-assignment. Testing that surfaced a much more fundamental bug: plain `$x = $x;` segfaulted perlc entirely. Root cause: `perl_assign()` freed the assignment target's old payload (`free(dst->sval)`) *before* reading/cloning from `src` (`strdup(src->sval)`); when `dst==src`, that free invalidated `src` too, so the following `strdup` read from memory that was already freed (and NULLed), crashing. Fixed by making `dst==src` a guaranteed no-op — self-assignment never needs to change anything, so skipping the free+reclone entirely is both correct and cheaper.

33. ~~**Fix D57: a self-recursive sub matching the AST-level inliner's shape hung/crashed the compiler at compile time**~~ — FIXED
    - Root cause: `tryEmitInline()` (codegen.cpp) unconditionally inlines any call whose target name is a key in `inlineSubs_` (subs whose body is exactly `my (@params) = @_; return expr;`), with no self-reference or cycle guard at all. For an ordinary (non-recursive) chain of inlinable subs this terminates fine, bounded by the finite number of subs in the program. But when the return expression being inlined contains a call back to the *same* sub (direct self-recursion) — or, transitively, to another inlinable sub that eventually calls back to it (mutual recursion) — `tryEmitInline()` recurses into itself operating on the exact same, unchanging AST node every time. This is *static, compile-time* infinite recursion in the compiler's own C++ call stack (not a runtime loop in the generated program), and was observed to crash with an LLVM "please submit a bug report" stack dump.     - Fix: restructured `compile()`'s inlineable-sub detection into two phases. Phase 1 is unchanged in spirit (same shape-matching logic as before) but now populates a local `candidates` map instead of `inlineSubs_` directly, so nothing becomes "live" for `tryEmitInline()` until cycle analysis has run. Phase 2 adds two new static helpers: `collectCalls(const Node &n, std::vector<std::string> &out)` walks every child-holding field of an expression subtree (same field set as `collectSubDefs`) and records the name of every `NK::Call` found; `dfsFindCycles(...)` runs standard 3-color DFS cycle detection (0=unvisited, 1=on the current DFS stack, 2=fully explored) over a call graph built by, for each candidate, calling `collectCalls()` on its body expression and keeping only edges whose target is *also* a candidate (an edge to a non-candidate sub can never be part of a cycle, since that call just becomes an ordinary bounded function call — no need to track it). Finding an edge back to a node still marked "on stack" means everything between that node and the top of the stack is in a cycle; a direct self-recursive sub is simply the degenerate case where the back-edge points at the node currently being visited.       - **Resource lifecycle**: `dlopen()`ed do-lib handles are tracked in a new `__thread` linked list (mirroring the pre-existing pattern used for XS module handles) and `dlclose()`d only at `perl_cleanup()` (process exit) — a do'd file's subs must stay callable for the rest of the process's lifetime, matching real Perl. 64. ~~**Fix D88: `callCtx_` (list-context propagation) leaked through scalar-forcing operators into a nested call, outside of print/printf**~~ — FIXED (2026-07-15)
    - Root cause: `callCtx_` is a blunt, unscoped, one-shot flag — set to `1` right before evaluating an entire RHS/argument expression tree at several call sites in `codegen.cpp` (list assignment RHS, lvalue array/hash-slice RHS, hash-from-list RHS, etc.), then read and immediately reset by whichever `Call`/`MethodCall`/`CallCodeRef` node's own codegen happens to be reached next — with no regard for how deeply nested that call is inside other operators. `my @a = (ctx() eq "x")` set `callCtx_=1` for the whole `(ctx() eq "x")` expression (since `my @a = ...` is a list-context assignment), and since no comparison/arithmetic/string `BinOp` codegen ever reset it before evaluating its own operands, `ctx()` (buried inside `eq`) incorrectly inherited list context — even though real Perl's `eq` (like every other comparison/arithmetic/string/bitwise operator) always evaluates both of its own operands in scalar context, regardless of the surrounding expression's own context. D12 (2026-07-14, item 56) had already fixed the identical class of leak specifically at print/printf's own call sites, via a narrow `CodeGen::isCallLikeForContext()` guard that only sets `callCtx_` when the immediate argument node is itself call-like — but that guard wasn't (and, by its own narrow design, couldn't be) applied to the *other* several places `callCtx_` gets set throughout the file.

Saving `callCtx_`, clearing it to `0` before evaluating each operand, and restoring the saved value afterward at that single choke point fixes the leak for this entire operator class in one place, for every current and future `callCtx_`-setting call site, without needing to touch or even enumerate them. Deliberately does NOT touch the separate `&&`/`\|\|`/`//`/`?:` branches earlier in `emitBinOp` — those operators' semantics are different from the plain scalar-forcing ones this fix targets: `&&`/`\|\|`'s left operand is always boolean-tested in scalar context, but its *right* operand, if reached, should transparently inherit whatever context the whole `&&`/`\|\|` expression itself is in (real Perl's actual behavior) — unconditionally forcing scalar context on both operands there, the way this fix does for `eq`/`+`/etc., would have been wrong.

      - **D93**: `sub f { return wantarray() ? The equivalent `if (wantarray()) { return (...) } else { return ... }` form works correctly, isolating the ternary form specifically as the trigger.
      - **D94**: `\|\|`'s right-hand operand, when reached, does not correctly inherit the outer expression's own list context — `my @a = (falsy() \|\| listret())` gives `listret()` scalar context instead of the list context real Perl would give it. The conceptual mirror image of D88 itself (D88: context leaking *through* an operator that should force scalar; D94: context *failing to pass through* an operator that should transparently forward it) — confirms this fix's deliberate choice not to touch the `\|\|`/`&&` branches was correct in spirit (there's a real, separate bug there already, unrelated to what this fix addresses).
